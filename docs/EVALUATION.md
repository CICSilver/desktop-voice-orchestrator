# 识别评估

目标：用一批带标注的录音，定量回答“唤醒不了”和“截断”到底发生在哪一环，而不是凭单次体验调参。
所有模型、阈值、端点参数的改动，都应该在同一批录音上重跑评估并对比结果。

## 1. 采集

1. 运行 `start_voice_frontend.bat`（或 `voice_frontend.exe live`），在调试台右上角点 **采集评估数据 ↗**。
2. 填说话人代号（不要写真实姓名），勾选要录的组，保持“采集期间停用系统动作”勾选。
3. 每组开始前页面会检查音箱输出：安静组要求没有播放，音乐组要求正在播放。
4. 每条先等 1.5 秒，然后显示要说的话。照着说完按 <kbd>空格</kbd>；说错按 <kbd>R</kbd> 重录，
   <kbd>S</kbd> 跳过，<kbd>Esc</kbd> 放弃本组。每组先录一段静默（音乐组为纯音乐）和 2 条不带唤醒词的
   负样本，用于统计误唤醒；它们排在所有命令之前，因此不会落进上一条命令的连续激活窗口，不需要额外等待。
5. 每组录成一个独立会话，结束时把 `labels.json` 写进 `data/sessions/<会话>/`。

默认的组：安静 · 0.5 米、播放音乐 · 0.5 米。每组 13 条命令（前置/后置唤醒、单条/多条命令）、2 条负样本和
1 段静默，约 2 分钟。每组的句子顺序固定，与勾选了哪些组无关。

误唤醒本身目前没有可感知的后果（播报只写日志，也不压低音乐）；只有唤醒后约 6 秒内的话恰好完整解析成命令才会
误执行。因此评估关注的是误执行，没有专门录读音相近的负样本。以后如果加入唤醒提示音或 TTS 播报，需要补测。

### 日常背景录音

负样本只有几十秒，说明不了长时间的误唤醒率。采集页底部的 **开始背景录音** 用来录一段日常使用的声音：

1. 设好时长（默认 60 分钟），点开始。它同样遵循“停用系统动作”的选项。
2. 照常用电脑：看视频、听歌、打电话、和人聊天、自言自语都可以，只是不说唤醒词。页面可以切到后台，
   但不要关闭，也不要让电脑睡眠。
3. 每 15 分钟自动保存成一个会话（`group.condition = "background"`），关页面或崩溃最多损失一段。
4. 不小心说了唤醒词、或者真的对它说了话，点 **排除刚才**（<kbd>X</kbd>）：前 30 秒到之后 10 秒记为
   `discarded`，不计入统计。
5. 到时长自动结束；也可以随时点 **结束并保存**。

评估时背景录音单独汇总为“日常背景 N 分钟 · 误唤醒 k 次（每小时 x 次）· 误执行 m 次”，并列出每次误唤醒在会话里的
时间和识别文本，便于回听。背景录音中的任何执行计划都算误执行，包括激活窗口内的后续话语，因为那个窗口只可能是
误唤醒打开的。一小时录音约占 1.9 GB 磁盘，评估大约需要十几分钟。

本工具只有一位使用者，因此不要求第二个说话人。为了避免“对着同一批录音调参”，每轮改进后应另录一批新的录音来验证，
调参用的录音和验证用的录音不要混用。

## 2. 评估

```powershell
.\build\windows-x64\Release\voice_frontend.exe evaluate data\sessions --out=data\evaluation-report.json
```

加 `--since=20260925-190000` 只评估从这个时刻起录的会话（会话目录名以创建时间开头），用来把验证批和调参批
分开统计；采集页结束时显示的命令已经带上了本次采集的起始时间。

`evaluate` 会找出目录下所有带 `labels.json` 的会话，逐个：

1. 用**当前配置**把会话完整回放一遍（与 `benchmark` 相同，强制 dry-run）；
2. 对每条录音的时间窗口，用全新的 KWS/ASR 实例分别在原始麦克风和 AEC 输出上做一次参考解码；
3. 按标注逐条打分，写入 `<会话>/evaluation.json`，并在控制台打印汇总和失败明细。

回放以“仅分析”速度运行时，每个音频包都会等流水线和 ASR 处理完上一个包再送入，结果与线程调度快慢无关；
回放也会等 ASR 模型加载完成后才开始。

## 3. 怎么读结果

| 字段 | 含义 |
| --- | --- |
| 唤醒召回 | 命令类录音中，流水线产生了未被抑制的唤醒的比例，分前置/后置 |
| 离线参考 | 同一窗口用全新 KWS 在原始麦克风 / AEC 输出上能否检出 |
| 漏唤醒原因 | **流水线**：离线参考能检出但线上没检出（状态重置、去抖、抑制等软件问题）；**模型**：离线参考也检不出（阈值、关键词 token、声学条件） |
| 命令正确 | 执行计划的动作序列与标注完全一致（含音量步长） |
| 缺字 · 切分截断 | 识别结果在开头/结尾缺字，且把该候选在这一侧多带 0.5 s 真实音频重新解码后能补回——说明是端点切得太早 |
| 缺字 · 模型丢字 | 缺字但延长候选也补不回。流式 Paraformer 对解码起点很敏感（同一句话起点挪 0.1–0.6 s 结果会变），这类属于识别模型问题，不应通过调端点参数解决 |
| 误唤醒 | 负样本和静默段里出现的唤醒次数 |
| 日常背景 | 背景录音的总时长、误唤醒次数与每小时次数、误执行次数 |

`evaluation.json` 的每条记录包含候选起止时间、识别文本、解析结果或拒绝原因、参考解码文本、麦克风语音电平
和音箱电平（用于核对该条是否真的在放音乐）。

## 4. 标注格式

`labels.json`（`schema: "dvo-eval-labels"`, `schema_version: 1`）：

```json
{
  "schema": "dvo-eval-labels", "schema_version": 1,
  "collection_id": "20260924-201500",
  "group": {"id": "quiet-near", "title": "安静 · 近距离", "condition": "quiet", "distance_m": 0.5},
  "speaker": "录制者", "wake_word": "小克", "complete": true,
  "takes": [
    {"id": "quiet-near-01-pre-pause", "kind": "command", "status": "ok", "attempt": 1,
     "prompt": "小克，暂停音乐", "text": "小克，暂停音乐", "wake_position": "prefix",
     "expected_actions": [{"type": "media.pause"}], "start_ms": 3120, "end_ms": 6480}
  ]
}
```

- `kind`：`command`（必须按 `expected_actions` 执行）、`negative`（有语音但不带唤醒词，不得唤醒或执行）、
  `silence`（无语音，不得唤醒）、`background`（日常背景，可长达一个会话；不做整段参考解码，
  逐次统计唤醒和执行）。
- `status`：只有 `ok` 计分；`discarded`（被重录）和 `skipped` 保留时间窗口但不计分。
- 时间以录音开始为零点，单位毫秒；也可以手写标注给旧录音补评估。

## 5. 离线试解析

`parse` 用当前配置的命令语法解析文本（每行一句，强制 dry-run），便于在不重放音频的情况下比较识别模型或解析器改动：

```powershell
"小克暂停音乐`n增加音量啊小克" | .\build\windows-x64\Release\voice_frontend.exe parse --wake=小克
```

## 6. 识别模型选型记录（2026-09-24）

同一批 52 条命令录音（安静/音乐 × 0.5 m/2 m），用流水线产生的候选片段逐一重新识别、再经 `parse` 判断动作是否完全正确：

| 整句识别模型 | 43 条已唤醒中命令正确 | 字错率 | 单句耗时 |
| --- | ---: | ---: | ---: |
| Online Paraformer（原方案） | 22 | 16.4% | — |
| Paraformer-zh 离线 int8 | 29 | 10.8% | ~51 ms |
| SenseVoice（Fun-ASR-Nano 转换）int8 | 31 | 9.6% | ~67 ms |
| Zipformer-CTC zh int8 | 30 | 7.7% | ~112 ms |
| Streaming Zipformer（+命令热词） | 19（26） | 17.3%（12.0%） | ~300 ms |
| SenseVoice，解析失败再用 Zipformer-CTC | 34 | — | — |

流式 Paraformer 的问题在于对解码起点敏感：同一段音频起点挪动 0.1–0.6 s，句尾字会时有时无；延长候选结尾不起作用。
因此整句识别改用非流式模型，流式模型只保留给调试台显示部分文本。接入后整条流水线重放：命令正确 21/52 → 34/52，
误唤醒与误执行仍为 0。

## 7. 唤醒与解析改进记录（2026-09-24）

同一批 52 条命令录音、12 条负样本，每一步都用 `evaluate` 整条流水线重放：

| 改动 | 命令正确 | 需唤醒的录音中唤醒成功 | 误唤醒 / 误执行 |
| --- | ---: | ---: | ---: |
| 原方案（流式 Paraformer 整句识别） | 21/52 | — | 0 / 0 |
| 整句识别改为 SenseVoice + Zipformer-CTC 备选 | 34/52 | — | 0 / 0 |
| 解析器容忍语气词、唤醒词误听一字、唤醒词另一侧的短残留、口吃重复 | 37/52 | — | 0 / 0 |
| 二级唤醒（`kws.asr_probe`） | 45/52 | 38/38 | 0 / 0 |

- 解析器的宽容读法只在严格读法失败时尝试，且每种读法都必须完整通过命令语法；被丢弃的一侧不得超过 3 个字，
  且自身不能解析成命令。唤醒词误听只在句首或句尾匹配。
- 二级唤醒命中后用原始麦克风音频识别（`asr_probe_source`），因为音乐播放时 AEC 输出对唤醒和识别都更差。
- 汇总中“落在激活窗口内”的录音是上一条命令的连续激活窗口仍打开时说的，按设计无需唤醒；负样本在窗口内被执行
  也单独列出，不计入误执行。
- 以上结果都在调参所用的同一批录音上得到。负样本只有 106 秒，还不能说明长时间误唤醒率；需要另录一批新的
  命令录音做验证，并录约 1 小时不含唤醒词的日常声音统计误唤醒。
- 以上录音的唤醒词是“小助手”。之后唤醒词改为“小克”（`x iǎo k è`），这批录音不能再用来评估唤醒，结果也不能和
  新唤醒词的录音直接比较。两个字的唤醒词不允许二级唤醒做“差一个字”的匹配（否则“小心”“小可爱”都会命中），
  识别文本里必须出现完整的“小克”；只有在 KWS 或二级唤醒已经确认唤醒之后，解析器才接受句首/句尾两个字里错一个
  的写法（如“小可，暂停音乐”）。

## 8. “小克”首批录音（2026-09-24，安静/音乐各 0.5 米，26 条命令）

| 改动 | 命令正确 | 需唤醒的录音中唤醒成功 | 误唤醒 / 误执行 |
| --- | ---: | ---: | ---: |
| 录制时配置（`vad.threshold = 0.25`） | 4/26 | 21/25 | 0 / 0 |
| `vad.threshold = 0.5` | 21/26 | 22/23 | 0 / 0 |
| 解析器接受“百分十”（识别丢了“之”） | 22/26 | 22/23 | 0 / 0 |

- 0.25 时语音要等概率低于 0.10 并持续 600 ms 才结束。约 -40 dBFS 的房间底噪、按键声、呼吸让语音段拖到下一句，
  相邻命令被并进同一个候选，后一条的唤醒又把前一条尚未结束的候选作废。0.35 与 0.5 的评分相同，但 0.5 的
  语音段结束得更贴近说话结束（多数在按键之前），离下一句的余量更大，命令也更早执行。
- 采集页原先在最后一条按下空格后立即停止录音，这条的候选来不及结束（上表中的 1 条“无候选”）；现在会多录 2.5 秒。
- 剩余失败都是音乐下的识别错误：“暂停”被识别为“参点”“再连”，“降低音量”被识别为“下个音乐”；以及 1 次模型漏唤醒。
- 阈值是在这批录音上选的，需要再录一批验证。
- 注意 `config/local.toml`（调试台“保存”生成）会覆盖 `default.toml` 里的同名参数；改默认值时要同时检查它。

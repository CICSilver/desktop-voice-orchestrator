# 项目计划

## 1. 项目目标

在 Windows 电脑上实现一个本地优先的桌面语音编排器。用户在电脑附近约 2 米处，可以说出一段包含多个操作的自然语言，并把自行录制的唤醒词放在整段话的开头或结尾。系统确认唤醒后，从同一段音频中恢复全部命令，生成有序动作计划，并按口述顺序执行。

### 目标能力

- 支持自定义唤醒词的录制、注册、测试和替换
- 支持 `唤醒词 + 命令序列` 与 `命令序列 + 唤醒词`
- 支持一次口述多个操作，保持语义顺序和执行顺序一致
- 支持 USB 音箱正在播放音乐时的语音输入
- 首批动作覆盖播放、暂停、上一首、下一首、打开指定软件和打开指定路径
- 默认离线运行，不把原始录音持久化
- 每次触发都有可查看的识别文本、动作计划和执行结果

### 非目标

- 第一阶段不追求跨房间远场拾音
- 第一阶段不支持任意软件中的任意 UI 操作
- 第一阶段不让通用大模型直接获得无限制的系统操作权限
- 第一阶段不承诺在所有音箱、麦克风和房间声学条件下达到同样效果

## 2. 成功标准

首个可用版本应在固定测试房间、固定 USB 音箱和目标麦克风上达到以下指标：

| 指标 | MVP 门槛 | 目标值 |
| --- | ---: | ---: |
| 0.5 米安静环境唤醒召回率 | 95% | 98% |
| 2 米安静环境唤醒召回率 | 90% | 95% |
| 2 米、音乐播放场景唤醒召回率 | 80% | 90% |
| 日常音频误唤醒 | 小于 1 次/8 小时 | 小于 1 次/24 小时 |
| 3 条命令保序执行成功率 | 85% | 95% |
| 前置唤醒端到端首动作延迟 | 小于 2.5 秒 | 小于 1.5 秒 |
| 后置唤醒端到端首动作延迟 | 小于 3.5 秒 | 小于 2.5 秒 |

上述数值必须通过可重复的录音集和现场测试得到，不能只以主观体验验收。

## 3. 总体方案

### 常驻链路

1. WASAPI 采集麦克风信号
2. WASAPI Loopback 采集 USB 音箱的实际播放参考信号
3. 对两个流做时间戳对齐、漂移补偿和 WebRTC AEC3 处理
4. 将净化后的人声转换为 16 kHz 单声道 PCM
5. 写入 20 秒内存环形缓冲区，同时运行 VAD 和 KWS

### 触发链路

1. KWS 检出唤醒词并返回时间区间和置信度
2. 根据唤醒词位置和 VAD 边界，从环形缓冲区截取同一段话
3. 对唤醒词之前、之后或两侧的有效语音进行 ASR
4. 文本规范化并切分为有序命令
5. 将命令映射成受约束的动作结构，先校验再执行
6. 串行执行动作，失败时按策略停止或继续

## 4. 里程碑

### M0：测试基线与录音集（第 1 周）

交付物：

- 目标电脑、USB 音箱、麦克风、房间布局和距离记录
- 安静、音乐、视频、键盘噪声等场景的测试矩阵
- 前置和后置唤醒各不少于 100 条的自录测试集
- 指标计算脚本和可重复的基准测试入口

退出条件：可以离线重放同一批录音并得到一致的指标报告。

### M1：双路采集与软件 AEC 可行性（第 2 至 3 周）

交付物：

- 麦克风 WASAPI Capture 与 USB 音箱 WASAPI Loopback 双路采集
- 统一时间基准、缓冲管理、采样率转换和通道转换
- WebRTC AEC3 集成，支持延迟参数和运行时统计
- 原始近端、远端参考、AEC 输出三路诊断录音开关

退出条件：音乐播放时，AEC 输出中的回放声显著下降且人声没有不可接受的失真；若失败，给出量化原因和硬件升级建议。

### M2：自定义唤醒词与双位置触发（第 4 至 5 周）

交付物：

- 唤醒词录制和样本管理工具
- KWS 模型或关键词图配置
- 前置/后置唤醒位置解析器
- 20 秒环形缓冲区和 VAD 话段边界逻辑
- 可选的说话人嵌入二次确认实验

退出条件：达到唤醒召回率和误唤醒的 MVP 门槛，且前置、后置两类测试均独立达标。

### M3：ASR 与多命令有序解析（第 6 至 7 周）

交付物：

- 本地中文 ASR 适配层和模型基准报告
- 标点、连接词、应用别名和路径别名规范化
- 受约束动作模型与确定性解析器
- 多命令的顺序编号、校验、预览和执行策略

退出条件：固定命令集上，三条命令的解析顺序正确率达到 95%，未知命令不会被猜测执行。

### M4：Windows 动作适配器（第 8 至 9 周）

交付物：

- GSMTC 媒体控制适配器
- 软件和路径启动适配器
- 基于配置的应用别名、路径别名和参数白名单
- 动作超时、取消、失败处理和审计日志

退出条件：播放/暂停/切歌/打开软件/打开路径端到端通过，任一步失败不会打乱剩余动作顺序。

### M5：产品化与现场验收（第 10 周）

交付物：

- 托盘程序、开机启动、麦克风状态与隐私提示
- 配置界面或配置工具
- 自动化回归测试和现场测试报告
- 安装包、卸载流程和故障排查文档

退出条件：连续运行 8 小时无崩溃、无音频设备泄漏，达到 MVP 指标并通过断网测试。

## 5. 模块划分

| 模块 | 建议语言 | 职责 |
| --- | --- | --- |
| `audio_frontend` | C++ | WASAPI、loopback、同步、AEC3、重采样、环形缓冲区 |
| `wakeword` | C++/Python | KWS、VAD、唤醒词位置和置信度 |
| `asr` | Python/C++ | 本地 ASR 推理、词时间戳和文本规范化 |
| `planner` | Python | 命令切分、别名解析、动作结构生成和校验 |
| `executor` | Python/C++ | 严格串行执行、超时、取消、日志和失败策略 |
| `windows_adapters` | C++/Python | GSMTC、ShellExecute、UI Automation 等系统适配 |
| `benchmark` | Python | 录音集重放、指标计算和回归报告 |

初期允许 C++ 音频前端以本地进程或动态库方式对 Python 暴露稳定接口；接口稳定后再决定是否合并为单一可执行程序。

## 6. 动作模型

编排器只执行白名单动作，不直接执行 ASR 文本。建议的最小结构如下：

```json
{
  "utterance_id": "uuid",
  "wake_position": "prefix",
  "actions": [
    { "sequence": 1, "type": "media.pause", "args": {} },
    { "sequence": 2, "type": "app.launch", "args": { "alias": "wechat" } },
    { "sequence": 3, "type": "path.open", "args": { "alias": "project" } }
  ]
}
```

执行前必须检查序号连续、动作类型已注册、参数来自白名单。默认策略为串行执行；普通动作失败时记录失败并继续，具有依赖关系或高风险的动作失败时停止后续动作。

## 7. 测试策略

- 单元测试：环形缓冲区回绕、时间戳换算、唤醒词切除、命令排序、别名解析
- 离线集成测试：把固定的麦克风流与 loopback 流重放到完整音频链路
- 端到端测试：真实播放音乐，分别在 0.5 米、1 米、2 米处说出固定脚本
- 耐久测试：设备切换、休眠恢复、USB 断连重连、8 小时连续运行
- 安全测试：未知应用、危险路径、ASR 幻觉、重复触发、执行中再次唤醒

所有模型、阈值或音频参数变更都应运行同一基准集，保存版本、设备信息和结果，避免凭单次体验调参。

## 8. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 麦克风与 loopback 时钟漂移 | AEC 随时间失效 | 使用设备时间戳、动态延迟估计和重采样补偿 |
| 音箱音量过大或房间混响强 | 2 米场景召回下降 | 先优化摆位与麦克风，再评估阵列或硬件 AEC |
| 自录样本过少 | 唤醒词过拟合、误触发高 | 引导多距离多语速录制，并加入负样本和真实背景音 |
| 后置唤醒前音频被截断 | 丢失前面的命令 | 环形缓冲区至少 20 秒，结合 VAD 向前寻找话段起点 |
| ASR 错词触发错误动作 | 桌面误操作 | 动作白名单、别名精确匹配、低置信度拒绝和危险动作确认 |
| 应用控制接口不统一 | 适配成本上升 | 优先 GSMTC 和系统 API，UI Automation 作为受控兜底 |

## 9. 首轮决策门

M1 结束时做第一次硬件决策：

- 若软件 AEC 在 2 米音乐场景达到门槛，继续使用现有麦克风和 USB 音箱
- 若主要问题是拾音信噪比，优先升级麦克风或麦克风阵列，而不是单独增加 AEC 芯片
- 若问题明确来自双设备时钟、延迟波动或非线性回声，且软件手段仍无法稳定，才评估集成硬件 AEC 的阵列设备

M2 结束时做模型决策：根据同一录音集的召回率、误触发、延迟、CPU 和内存数据，在候选 KWS/ASR 实现中定版，不提前绑定单一模型。

## 10. 待确认事项

- 目标麦克风的具体型号、采样率和通道数
- 用户希望录制的唤醒词长度、语言和样本数量
- 需要适配的首批软件清单及其启动方式
- 高风险动作是否需要语音二次确认
- 可接受的 CPU、内存占用和端到端延迟上限

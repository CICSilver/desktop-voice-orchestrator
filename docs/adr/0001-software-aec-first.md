# ADR-0001：软件 AEC 优先

- 状态：已接受，用于原型阶段
- 日期：2026-07-13

## 背景

系统的扬声器通过 USB 直接连接 Windows 电脑。需要在音乐播放时，从约 2 米距离拾取语音，并支持把唤醒词放在命令末尾。后置唤醒意味着在唤醒发生前无法通过降低音量来改善全部命令音频，因此回声处理必须位于常驻缓冲区之前。

候选方案包括：

1. 直接采购带 XVF3800 等硬件 AEC 的阵列设备
2. 使用 WASAPI Loopback 获取电脑实际播放信号，配合 WebRTC AEC3 做软件回声消除
3. 仅依赖麦克风指向性、降噪或播放时自动降低音量

## 决策

原型阶段选择方案 2。使用麦克风 WASAPI Capture 和 USB 音箱 render endpoint 的 WASAPI Loopback 作为 AEC 的近端与远端输入，在 Windows 上完成时间戳对齐、延迟估计、漂移补偿和 WebRTC AEC3 处理。

XVF3800 不作为初始必需硬件。它集成的 AEC、波束形成、自动增益和降噪能力在一体化远场阵列中有价值，但对于“电脑已经能够取得精确播放参考信号”的场景，直接加入会与软件链路形成功能重叠，还会增加成本、USB 音频路由、固件调试和硬件供应风险。

## 理由

- USB 音箱的播放参考信号可由系统 loopback 获得，不需要额外模数链路
- 软件方案便于记录中间信号、调整参数、做离线重放和量化对比
- 不提前绑定特定麦克风阵列和供应商
- 先用真实房间数据判断问题来自回声、拾音信噪比、混响还是时钟漂移，避免用硬件掩盖错误诊断
- 对后置唤醒，AEC 输出可以直接进入常驻环形缓冲区，链路更清晰

## 代价

- 麦克风与 USB render endpoint 可能由不同硬件时钟驱动，需要处理长期漂移
- Windows 调度和设备缓冲会造成可变延迟，必须持续估计而不是写死参数
- 音箱、功放或系统音效产生的非线性失真会降低线性 AEC 效果
- CPU 占用和实时稳定性由本项目负责

## 升级条件

完成 M1 基准测试后，出现下列情况之一才重新评估硬件 AEC：

- 延迟和漂移补偿正确后，音乐场景仍无法达到唤醒和 ASR 门槛
- 目标麦克风的 2 米拾音信噪比明显不足，且更换普通麦克风仍不能解决
- 产品需要稳定的阵列波束形成，而不只是回声消除
- 设备部署要求脱离特定 Windows 音频拓扑或减少主机 CPU 占用

即使升级，也应优先选择能直接输出处理后 USB 音频并提供可量化调试接口的整机阵列，而不是只为了“有 AEC 芯片”增加一个与现有音频路径难以同步的模块。
